# BR-33: Payment Webhook Idempotency

| Field | Value |
|---|---|
| ID | BR-33 |
| Category | Checkout & Payment |
| Enforced by | Application + Database (`UQ_PaymentTransactions_BankReference`, `UX_Orders_TransactionCode`) |
| Source feature(s) | CHK-06 |
| Used by | [UC-36](../use-cases/UC-36.md), [UC-57](../use-cases/UC-57.md), [UC-71](../use-cases/UC-71.md) |

## Rule

A payment webhook is processed only if it is authentic and has not been processed before.

## Details

- The webhook must pass verification (API key or signature) before anything is read from it.
- Every verified transaction is recorded in `PaymentTransactions` with its bank reference, which is unique (BR-42). A transaction whose bank reference is already recorded is acknowledged without making changes.
- Recording the transaction and marking the order `Paid` happen in one database transaction, so one is never saved without the other.
- The order is marked `Paid` with a conditional update (`WHERE PaymentStatus = 'Unpaid' AND OrderStatus <> 'Canceled'`), so a webhook and the expiry job (BR-41) cannot both succeed.
- A webhook never deducts stock, increases voucher usage or `SoldCount`; those happen only at order placement (BR-30).
- A bank reference can pay at most one order: `Orders.TransactionCode` has a filtered unique index (`UX_Orders_TransactionCode`).
